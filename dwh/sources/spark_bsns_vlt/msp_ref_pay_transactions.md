# spark_bsns_vlt.msp_ref_pay_transactions

## Назначение таблицы

`spark_bsns_vlt.msp_ref_pay_transactions` содержит платежные транзакции пользователей Freedom Media: успешные и неуспешные попытки оплаты, возвраты, технические операции с картой, суммы счетов, статусы, платежные методы, данные мерчанта и технические поля загрузки.

Таблица нужна для анализа оплат и монетизации: выручки, успешных платежей, возвратов, первых и повторных оплат, связки оплат с подписками, проверки тестовых платежей и контроля качества платежных данных.

## Гранулярность

Одна строка = одна запись платежной операции из платежного источника. На текущих данных поле `id` уникально, но `order_id` и `transaction_id` могут повторяться, поэтому их не стоит считать уникальным ключом без дополнительной проверки.

В таблице есть не только успешные оплаты. Встречаются статусы `success`, `incomplete`, `error`, `waiting`, `new`, `process`, а также тестовые операции и возвраты. Для расчета выручки обычно нужно отбирать только успешные не-тестовые платежи и отдельно решать, как учитывать технические суммы и возвраты.

## Логика из SQL-витрины

Скрипт `dwh/datamarts/pay_transaction.sql` строит производную витрину на основе `msp_ref_pay_transactions`, `msp_ref_users` и восстановленного телефона пользователя.

Основная логика:

- из `msp_ref_users` берется по одному телефону на `user_id`;
- из платежей берутся только строки `p.status in ('success')`;
- телефон платежа восстанавливается как `coalesce(p.user_phone, u.phone)`, где `u.phone` подтягивается по условию `p.param1 = u.user_id::varchar`;
- телефон очищается от нецифровых символов через `regexp_replace(..., '[^0-9]', '', 'g')`;
- если телефона нет, он дополнительно восстанавливается по `pan_mask`: для одной маски карты выбирается телефон из других успешных платежей;
- телефон нормализуется заменой начальной `8` на `7`;
- платежи агрегируются по `phone`, `order_id`, `merchant_id`: считается сумма `bill_amount` как `price`, минимальная дата создания как `cr_date`, максимальный `bank_alias`;
- в конце результат связывается с `msp_ref_users` по нормализованному телефону и получает `user_id`.

Важно: в этом скрипте нет фильтра `test_mode = false` и нет исключения технических сумм. Если витрина используется для аналитики выручки, эти условия нужно добавлять отдельно в запросах или явно согласовать бизнес-правило.

## Правило идентификации пользователя по мерчанту

Для связки платежной транзакции с пользователем нельзя универсально использовать одно и то же поле для всех мерчантов:

- для `merchant_id = 563748` идентификатор пользователя нужно восстанавливать по телефону: брать `user_phone` из платежа, нормализовать номер и связывать с пользовательскими/подписочными таблицами по телефону;
- для остальных мерчантов `param1` используется как `user_id`, если значение числовое и находится в `msp_ref_users.user_id` или подписочных витринах;
- поле `param1` для `merchant_id = 563748` не нужно трактовать как надежный `user_id`;
- телефон является персональными данными, поэтому его можно использовать только внутри SQL-связки и не выводить в аналитические отчеты, ноутбуки и выгрузки.

Это правило особенно важно для анализа SuperApp/merchant-сценариев и платежных попыток: если для `merchant_id = 563748` искать пользователя только через `param1`, часть транзакций будет ошибочно не связана с пользователем.

## Основные сценарии использования

- анализ количества успешных платежей и суммы оплат по дням;
- расчет выручки по мерчантам, платежным методам, банкам и пользователям;
- поиск первой успешной оплаты пользователя;
- анализ повторных платежей и продлений подписки;
- связь платежей с подписками из `spark_bsns_vlt.msp_ref_subscriptions`;
- исключение тестовых и технических платежей из отчетности;
- контроль дублей, пропусков телефонов, повторяющихся `order_id` и возвратов;
- сверка платежных данных с внешним платежным провайдером по `transaction_id`, `reference`, `approval_code`, `receipt_number`.

## Ключевые поля для аналитики

- `id` - уникальный идентификатор строки платежной операции.
- `status` - главный фильтр успешности платежа; для факта оплаты обычно `status = 'success'`.
- `test_mode` - обязательный фильтр для исключения тестовых платежей.
- `bill_amount` - сумма платежного движения; перед расчетом выручки нужно исключить технические суммы и обработать возвраты.
- `payment_date`, `complete_date`, `created_at` - даты платежа, завершения и создания попытки оплаты.
- `payment_type`, `type` - тип платежной операции: оплата, возврат, рекуррентная операция, привязка или проверка карты.
- `merchant_id`, `merchant_name`, `merchant_payment_system_name` - поля для анализа по мерчанту и платежной системе.
- `param1` - ключ связи с `msp_ref_users.user_id` для мерчантов, отличных от `563748`, если значение числовое.
- `user_phone` - ключ связи по телефону для `merchant_id = 563748`; персональные данные, требует нормализации и не должен выводиться в отчеты.
- `order_id`, `transaction_id`, `reference`, `approval_code`, `receipt_number` - технические ключи для сверки с платежной системой и источниками.
- `t_w_loaddate`, `t_w_loadid`, `t_w_crdate` - технические поля загрузки и контроля свежести.

## Фильтры для аналитических запросов

Базовый фильтр для реальных успешных платежей:

```sql
where status = 'success'
  and test_mode = false
```

Для расчета выручки этого фильтра может быть недостаточно. В текущих данных среди успешных не-тестовых операций много платежей на `5`, `10`, `100` тенге, есть отрицательные суммы и строки с возвратами. Такие операции могут быть техническими, тестовыми бизнес-сценариями, проверочными списаниями, возвратами или балансовыми движениями. Их нельзя автоматически считать регулярной выручкой.

Рекомендуемый подход:

- сначала отделить успешные операции: `status = 'success'`;
- исключить тестовый режим: `test_mode = false`;
- отдельно обработать возвраты: `payment_type` с refund-сценариями, `refund_amount`, `refund_date`, отрицательные `bill_amount`;
- проверить минимальную сумму платежа для конкретного продукта или тарифа;
- не считать технические операции `add_card` и `approve_card` оплатой подписки без дополнительного условия;
- для отчетов по дням выбрать одну дату: чаще `payment_date` или `complete_date`, а не `created_at`;
- не выводить `user_phone`, `user_email`, `pan_mask` в аналитические выгрузки.

Пример более осторожного фильтра для валовой выручки:

```sql
where status = 'success'
  and test_mode = false
  and type = 'pay'
  and bill_amount > 0
  and payment_type not like '%refund%'
```

Если нужно исключить технические маленькие суммы, порог и список исключений должны быть согласованы с бизнесом. По SQL-скрипту невозможно однозначно определить, какие суммы считать техническими для всех периодов.

## Связь с другими таблицами

### Связь с `spark_bsns_vlt.msp_ref_users`

В `pay_transaction.sql` используется два способа связки, но при прямом анализе платежей нужно учитывать `merchant_id`.

1. Для мерчантов, отличных от `563748`, по `param1` как `user_id`:

```sql
p.param1 = u.user_id::varchar
```

2. Для `merchant_id = 563748`, по нормализованному телефону:

```sql
regexp_replace(p.user_phone, '[^0-9]', '', 'g') = regexp_replace(u.phone, '[^0-9]', '', 'g')
```

Затем телефон дополнительно нормализуется заменой начальной `8` на `7`.

Ограничение: `param1` не всегда является числовым `user_id`, а телефон может отсутствовать или быть записан в разном формате. Для надежной связки важно сначала разделить платежи по `merchant_id`: `563748` связывать по телефону, остальные мерчанты - по `param1` как `user_id`.

### Связь с `spark_bsns_vlt.msp_ref_subscriptions`

Прямого `subscription_id` в `msp_ref_pay_transactions` нет. Связка с подписками возможна, но не идеальна:

- по `user_id`, если он восстановлен через `param1` или через `msp_ref_users`;
- по телефону, если он нормализован одинаково в платежах и подписках;
- по близости дат платежа к `start_date` подписки;
- по провайдеру/мерчанту и сумме, если это соответствует бизнес-правилам.

Не стоит считать, что каждый платеж однозначно связан с одной подпиской. Возможны оплаты без найденной подписки и подписки без найденного платежа.

## Особенности и ограничения

- В таблице есть тестовые платежи: для аналитики реальных оплат нужен `test_mode = false`.
- В таблице есть неуспешные попытки платежей: `incomplete`, `error`, `waiting`, `new`, `process`.
- Есть возвраты и отрицательные суммы; для net revenue нужно учитывать `refund_amount`, `refund_date`, `payment_type` и знак `bill_amount`.
- Малые суммы, особенно `5`, `10`, `100`, требуют отдельного бизнес-правила: они могут существенно влиять на количество платежей, но не обязательно отражают регулярную выручку подписок.
- `merchant_name` и `bank_alias` текстовые и неоднородные; для стабильной группировки лучше использовать идентификаторы и справочники нормализации.
- `user_phone`, `user_email`, `pan_mask` являются чувствительными данными. Их нельзя выводить в отчетах и широких аналитических выгрузках.
- `param1` может быть полезен для связи с пользователем, но только для мерчантов, где он действительно хранит `user_id`; для `merchant_id = 563748` использовать телефон.
- `created_at` отражает создание платежной записи/попытки, а не всегда факт завершения оплаты. Для финансовой аналитики чаще проверять `payment_date` и `complete_date`.
- `order_id` и `transaction_id` могут повторяться, поэтому перед дедупликацией нужно определить бизнес-ключ платежа.

## Примеры SQL-запросов

### 1. Количество успешных платежей и сумма оплат по дням

```sql
select
    complete_date::date as payment_day,
    count(*) as payments_count,
    sum(bill_amount) as gross_amount
from spark_bsns_vlt.msp_ref_pay_transactions
where status = 'success'
  and test_mode = false
  and type = 'pay'
  and bill_amount > 0
  and payment_type not like '%refund%'
group by complete_date::date
order by payment_day;
```

### 2. Первая успешная оплата пользователя с учетом правила `merchant_id`

```sql
with successful_payments as (
    select
        case
            when merchant_id = 563748 then null
            when param1 ~ '^[0-9]+$' then param1::numeric
        end as user_id,
        case
            when merchant_id = 563748
            then regexp_replace(user_phone, '[^0-9]', '', 'g')
        end as normalized_phone,
        case
            when merchant_id = 563748
            then md5(regexp_replace(user_phone, '[^0-9]', '', 'g'))
            when param1 ~ '^[0-9]+$'
            then param1
        end as analytics_user_key,
        id as payment_id,
        merchant_id,
        complete_date,
        bill_amount,
        row_number() over (
            partition by
                case
                    when merchant_id = 563748 then regexp_replace(user_phone, '[^0-9]', '', 'g')
                    when param1 ~ '^[0-9]+$' then param1
                end
            order by complete_date, id
        ) as rn
    from spark_bsns_vlt.msp_ref_pay_transactions
    where status = 'success'
      and test_mode = false
      and complete_date is not null
      and (
          (merchant_id = 563748 and user_phone is not null)
          or (merchant_id <> 563748 and param1 ~ '^[0-9]+$')
      )
)
select
    user_id,
    analytics_user_key,
    payment_id,
    merchant_id,
    complete_date as first_payment_date,
    bill_amount as first_payment_amount
from successful_payments
where rn = 1;
```

### 4. Связь платежей с подписками по пользователю и дате

```sql
with payments as (
    select
        param1::integer as user_id,
        null::text as normalized_phone,
        id as payment_id,
        merchant_id,
        complete_date,
        bill_amount
    from spark_bsns_vlt.msp_ref_pay_transactions
    where status = 'success'
      and test_mode = false
      and complete_date is not null
      and merchant_id <> 563748
      and param1 ~ '^[0-9]+$'

    union all

    select
        null::integer as user_id,
        regexp_replace(user_phone, '[^0-9]', '', 'g') as normalized_phone,
        id as payment_id,
        merchant_id,
        complete_date,
        bill_amount
    from spark_bsns_vlt.msp_ref_pay_transactions
    where status = 'success'
      and test_mode = false
      and complete_date is not null
      and merchant_id = 563748
      and user_phone is not null
),
subscriptions as (
    select
        user_id,
        regexp_replace(phone, '[^0-9]', '', 'g') as normalized_phone,
        start_date,
        end_date,
        type,
        packet,
        provider
    from spark_bsns_vlt.msp_ref_subscriptions
    where user_id is not null
)
select
    p.user_id,
    p.payment_id,
    p.complete_date,
    p.bill_amount,
    s.start_date,
    s.end_date,
    s.type as subscription_type,
    s.packet,
    s.provider
from payments p
left join subscriptions s
    on p.user_id = s.user_id
   and p.complete_date >= s.start_date - interval '1 day'
   and p.complete_date <  s.start_date + interval '1 day'
where p.merchant_id <> 563748

union all

select
    s.user_id,
    p.payment_id,
    p.complete_date,
    p.bill_amount,
    s.start_date,
    s.end_date,
    s.type as subscription_type,
    s.packet,
    s.provider
from payments p
left join subscriptions s
    on p.normalized_phone = s.normalized_phone
   and p.complete_date >= s.start_date - interval '1 day'
   and p.complete_date <  s.start_date + interval '1 day'
where p.merchant_id = 563748;
```

## Итоговое краткое описание

`spark_bsns_vlt.msp_ref_pay_transactions` - основная таблица платежных операций Freedom Media. Она подходит для анализа успешных оплат, выручки, возвратов, первых и повторных платежей, а также для связи монетизации с подписками. Главные поля для аналитики: `id`, `status`, `test_mode`, `bill_amount`, `payment_date`, `complete_date`, `payment_type`, `merchant_id`, `param1`, `user_phone`. Для корректных отчетов обязательно фильтровать `status = 'success'`, исключать `test_mode = false`, отдельно обрабатывать возвраты, отрицательные и малые технические суммы. Связь с пользователем зависит от мерчанта: для `merchant_id = 563748` использовать нормализованный телефон, для остальных мерчантов - `param1` как `user_id`; связь с подписками возможна через восстановленный `user_id`, телефон и даты, но не является идеальной и требует проверок качества.
