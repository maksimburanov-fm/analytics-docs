# spark_bsns_vlt.msp_ref_tv_session

## Назначение

Таблица содержит TV/live/catchup-просмотры пользователей OTT-сервиса: факты просмотра телеканалов, в отличие от VOD-сессий с конкретным фильмом или эпизодом. Используется для анализа tv-потребления, вовлеченности в телеканалы, сравнения TV и VOD поведения и оценки влияния tv-просмотров на продление подписки.

По агрегатной проверке в таблице 11 273 014 строк. Период по `session_start_ts`: с `2024-05-22 16:01:22` по `2026-07-01 23:59:52`.

## Гранулярность

Одна строка = один факт TV-просмотра канала пользователем. По структуре таблицы строка похожа на TV-сессию: есть `session_start_ts`, `session_end_ts`, `duration_s`, `tv_session_id`, `user_id` и `channel_id`.

Важно: в таблице есть окончание сессии (`session_end_ts`) и оно заполнено во всех проверенных строках, но `duration_s` отсутствует в 5 299 805 строках. Поэтому строку лучше трактовать как факт/событие TV-просмотра с доступными границами времени, а не как всегда надежный полный просмотр. Для live TV возможны разрывы, переключения каналов и технические повторы событий.

## Ключевые поля

- `user_id` - идентификатор пользователя для связи с подписками и агрегации TV-поведения до уровня пользователя.
- `channel_id` - основной идентификатор телеканала.
- `channel_title` - текстовое название канала для отображения и быстрых топов.
- `session_start_ts` - основное поле времени для привязки TV-просмотра к дню, периоду подписки и retention.
- `tv_session_id` - технический идентификатор TV-сессии; полезен для дедупликации, но не гарантирует уникальность строки.

## Поля времени

- `session_start_ts` - дата и время начала TV-просмотра. Это источник истины для календарной даты TV-активности и попадания просмотра в период подписки.
- `session_end_ts` - дата и время окончания TV-просмотра. Поле существует и заполнено, но для live TV его нужно проверять: завершение сессии может фиксироваться неточно из-за переключений каналов, разрывов или особенностей клиента.
- `t_w_crdate` - техническая дата создания записи в DWH.
- `t_w_loaddate` - техническая дата загрузки записи в DWH.

Приближенную длительность просмотра можно оценивать двумя способами:

- Основной способ: считать `extract(epoch from (session_end_ts - session_start_ts))`, если `duration_s is null`, `session_end_ts >= session_start_ts` и результат не выглядит аномальным.

Для TV-аналитики источник истины по watch time нужно явно фиксировать в методологии, потому что `duration_s` отсутствует почти в половине строк, а live-сессии могут дробиться или завершаться технически.

## Производные метрики

- Количество TV-сессий: `count(*)` для количества строк или `count(distinct tv_session_id)` для приближенного количества уникальных TV-сессий. В таблице 11 273 014 строк и 11 030 856 distinct `tv_session_id`, поэтому метод подсчета нужно фиксировать.
- Количество активных дней с TV: `count(distinct date(session_start_ts))` на уровне `user_id` или нужного сегмента.
- Приближенный watch time в часах: `sum(duration_s) / 3600.0` по строкам, где `duration_s > 0`. Для строк с пустым `duration_s` можно отдельно добавить fallback по timestamps, но такие часы нужно помечать как оценочные.
- Уникальные каналы: `count(distinct channel_id)` на уровне `user_id`, подписки или периода анализа.
- Сессии по каналам: `count(*)` или `count(distinct tv_session_id)` в разрезе `channel_id`/`channel_title`.
- Доля TV в общем потреблении: TV watch time или TV sessions из этой таблицы делятся на сумму TV + VOD метрик, где VOD берется из `spark_bsns_vlt.msp_content_session`.

## Проверки качества данных

- Пропуски `user_id`: 0 строк. Поле можно использовать для связи с подписками.
- Пропуски `channel_id`: 0 строк. Поле можно использовать как основной ключ канала.
- Пропуски `channel_title`: 0 строк. Поле можно использовать для отображения, но для join лучше `channel_id`.
- Пропуски `session_start_ts`: 0 строк.
- Пропуски `session_end_ts`: 0 строк.
- `duration_s is null`: 5 299 805 строк. Watch time по TV без fallback будет неполным.
- `duration_s <= 0`: 0 строк. Минимальное заполненное значение `duration_s` = 1 секунда.
- `session_end_ts < session_start_ts`: 0 строк.
- Аномально длинные сессии: 165 строк с `duration_s > 6 часов`, 141 строка с `duration_s > 24 часа`; максимальное `duration_s` = 615 220 секунд. Для watch time рекомендуется каппинг или отдельная фильтрация.
- Дубли `tv_session_id`: 194 742 идентификатора встречаются больше одного раза, всего 436 900 строк с повторяющимися `tv_session_id`, максимум 7 151 строка на один `tv_session_id`.
- Дубли по ключу события `user_id + channel_id + session_start_ts`: 348 796 повторяющихся ключей, 740 011 строк в таких повторах, максимум 56 строк на один ключ события.
- Слишком частые события: максимум 252 события на одного пользователя за одну минуту; найдено 96 973 пользователь-минут с 10+ событиями, 3 579 с 30+ событиями и 479 с 60+ событиями. Такие всплески похожи на переключение каналов, повторы клиента или технический шум.
- Аномальные пики по каналам нужно контролировать через долю топ-каналов. В агрегатах самые частые каналы: `Freedom Media 1` - 1 281 807 строк, `Setanta Sports 1` - 919 400 строк, `Седьмой канал` - 533 234 строки. Резкие изменения долей этих каналов по дням стоит проверять отдельно.

## Ограничения

- Точная длительность TV-просмотра ограничена: `duration_s` пустой в 5 299 805 строках, а расчет через timestamps может отражать техническую сессию, а не фактическое внимание пользователя.
- Возможны разрывы TV-сессий из-за переключений каналов, закрытия приложения, фонового режима или потери соединения.
- Конец просмотра трудно определить идеально: `session_end_ts` есть, но для live-потока он может быть техническим временем фиксации, а не фактическим моментом прекращения просмотра.
- Возможен шум от быстрого переключения каналов: в данных есть пользователь-минуты с десятками и сотнями событий.
- `tv_session_id` не является строгим уникальным идентификатором строки или просмотра; перед `count(distinct tv_session_id)` нужна проверка дублей.
- EPG-поля заполнены слабо: `epg_id`, `epg_original_title`, `epg_genres_en`, `epg_genres_kz` нельзя считать надежной основой для регулярной аналитики программ и жанров.
- `origin_ip` и `device_id` не должны выводиться значениями в отчетах; использовать только в агрегированном или техническом контексте при наличии прав доступа.

## Отличия от VOD

По сравнению с `spark_bsns_vlt.msp_content_session` TV-таблица описывает tv-просмотр каналов, а не просмотр конкретного VOD-контента.

- Гранулярность: в VOD строка = сессия просмотра конкретного контента (`content_id`, `content_title`, `content_type`); в TV строка = факт/сессия просмотра телеканала (`channel_id`, `channel_title`).
- Watch time: в VOD `duration_s` тоже может быть пустым, но сессия привязана к конкретному контенту. В TV длительность менее точна из-за live-потока, переключений каналов и сложного определения конца просмотра.
- Контентная аналитика: в VOD основной объект анализа - фильм, серия или сериал; в TV основной объект - канал, а EPG-программа заполнена неполно.
- Шум: TV-данные более чувствительны к быстрым переключениям каналов и техническим повторам событий.
- Точность данных: VOD лучше подходит для анализа просмотра конкретного контента, TV лучше подходит для оценки live-активности, дней с TV и интереса к каналам/спорту/эфирам.
