# spark_dm.subscriptions_with_revenue

## Назначение

`spark_dm.subscriptions_with_revenue` - витрина подписок с платежным контекстом и фильтрацией тестовых/служебных подписок. Она нужна для аналитики подписочного цикла, выручки и продлений, когда важно отличать реальные платежные продления от ручных подписок, trial/promo и партнерского биллинга.

Для исследования влияния поведения на продление эта витрина должна заменить прямое использование `spark_bsns_vlt.msp_ref_subscriptions`, потому что:

- исключает тестовых пользователей и тестовые/служебные пакеты;
- нормализует источник подписки через расчетный `provider_id`;
- подтягивает платежную транзакцию, если она есть;
- помечает ручные подписки через `payment_status = 'manual'`;
- позволяет отдельно анализировать Freedom Media и Super App.

SQL формирования находится в `dwh/datamarts/SUBSCRIPTIONS_WITH_REVENUE.sql`.

## Гранулярность

Одна строка = одна подписка пользователя после фильтрации тестовых и служебных записей.

По агрегатной проверке в таблице 2 400 948 строк и 359 027 пользователей. Период по `start_date`: с `2024-09-02` по `2026-07-02`.

## Источники данных

- `spark_bsns_vlt.msp_ref_subscriptions` - основной источник подписок: пользователь, даты подписки, тип, пакет, провайдер, стоимость.
- `spark_dm.pay_transactions` - платежные транзакции: цена, дата платежа, банк/канал оплаты. Используется для определения факта платежа и источника оплаты.
- `spark_bsns_vlt.msp_ref_users` - справочник пользователей. Используется только для исключения тестовых пользователей (`user_role = 'test'`).

## Логика формирования

### pay_tr

CTE `pay_tr` берет транзакции из `spark_dm.pay_transactions`.

Правила:

- исключаются технические/малые платежи `price in (10, 100, 500)`;
- `bank_alias` нормализуется:
  - `merchant_id = 563748` -> `superapp`;
  - `bankfreedomfinancekazakhstanjointstockcompan` -> `freedom`;
  - `jsckaspibank` -> `kaspi`;
  - `halyksavingsbankofkazakhstan` -> `halyk`;
  - иначе остается исходный `bank_alias`;
- рассчитывается `rn = row_number() over (partition by phone, cr_date order by price)` для сопоставления нескольких транзакций и подписок в один день.

### sub_base

CTE `sub_base` берет подписки из `spark_bsns_vlt.msp_ref_subscriptions`.

Фильтры:

- исключаются пакеты `packet_id not in (1, 2, 3, 5, 6, 8, 11, 13, 15, 17, 18, 19, 53, 55, 63, 67, 68, 69, 70)`;
- исключаются провайдеры `provider_id not in (2, 3, 5, 6, 7, 44, 42, 45)`;
- исключаются нулевые подписки `end_date::date - start_date::date != 0`;
- исключаются тестовые пользователи из `msp_ref_users`, где `user_role = 'test'`.

Расчетные поля:

- `duration = end_date::date - start_date::date`;
- `first_sub_dt = min(start_date) over (partition by user_id order by start_date)`;
- `last_sub_dt = max(end_date) over (partition by user_id order by end_date desc)`;
- `sub_num = row_number() over (partition by user_id order by start_date)`;
- `subscription_type`: `Промокод`, `Триальный период`, `Платная`;
- нормализованный `source` по `packet_id`;
- нормализованный `provider_id` по `packet_id`;
- `real_provider` и `real_provider_id` сохраняют исходные значения из source-таблицы;
- `rn = row_number() over (partition by phone, start_date order by value)` для join с платежами.

### sub_with_pay

CTE `sub_with_pay` соединяет подписки с платежами:

```sql
s.phone = p.phone
and s.rn = p.rn
and s.start_date = p.cr_date
```

Правила цены и канала оплаты:

- для `packet_id in (7, 60)` цена фиксируется как `25`;
- для `packet_id = 64` цена фиксируется как `450`;
- иначе используется `p.price` из транзакций;
- для `packet_id in (7, 60, 64)` `bank_alias = 'partner_billing'`;
- если транзакция не найдена, `bank_alias = 'no_transaction'`;
- иначе используется нормализованный `bank_alias` из платежей.

### payment_types

CTE `payment_types` рассчитывает `payment_status`:

- `manual` - если `price is null or price = 0` и `sub_type not in ('trial', 'promo')`;
- `promo/trial` - если `sub_type in ('trial', 'promo')`;
- `full_price` - все остальные подписки с платежом.

Это ключевое поле для анализа продления: `manual` нужно исключать или анализировать отдельно, потому что такие подписки могли быть навешаны вручную, например из-за проблем с рекуррентными платежами SuperApp.

### std_duration

Через список стандартных длительностей `1, 14, 30, 60, 90, 120, 180, 365, 777` для каждой подписки выбирается ближайшая `std_duration`:

```sql
order by abs(p.duration - std_duration), std_duration desc
limit 1
```

Это позволяет сгруппировать фактические длительности подписок в стандартные периоды.

## Основные поля

| Поле | Тип | Описание | Использование в аналитике |
|------|-----|----------|---------------------------|
| real_provider | character varying(1000) | Исходное название провайдера из `msp_ref_subscriptions.provider`. | Аудит исходного источника и сравнение с нормализованным `provider_id`. |
| price | numeric | Цена подписки после сопоставления с платежом или фиксированного правила для партнерских пакетов. Если платеж не найден, заменяется на `0`. | Расчет выручки, ARPU, отделение платных подписок от ручных. |
| std_duration | integer | Ближайшая стандартная длительность подписки. | Группировка подписок по стандартным периодам: 1, 14, 30, 60, 90, 120, 180, 365, 777 дней. |
| duration | integer | Фактическая длительность подписки в днях: `end_date - start_date`. | Контроль длительности и расчет периода первой подписки. |
| provider_id | integer | Нормализованный идентификатор провайдера/источника, рассчитанный по `packet_id`. | Основное поле для фильтрации Freedom Media, Super App и других источников в аналитике. |
| subscription_type | text | Бизнес-тип подписки: `Промокод`, `Триальный период`, `Платная`. | Сегментация trial/promo/paid. |
| phone | character varying(100) | Телефон пользователя из source-таблицы. Персональные данные. | Не выводить в отчетах и исследовательских датасетах; используется внутри витрины для join с платежами. |
| sub_type | character varying(100) | Исходный тип подписки: `trial`, `promo`, `subscribe`, `purchase`, `renew` и др. | Определение жизненного цикла подписки и типа продления. |
| sub_num | bigint | Номер подписки пользователя по `start_date`. | Определение первой подписки (`sub_num = 1`) и последующих подписок. |
| first_sub_dt | date | Дата первой подписки пользователя. | Когортный отбор пользователей по первой подписке. |
| last_sub_dt | date | Дата окончания последней подписки пользователя. | Анализ текущего жизненного цикла и давности последней подписки. |
| packet | character varying(500) | Название пакета/тарифа. | Анализ по тарифам и пакетам. |
| payment_status | text | Статус оплаты: `manual`, `promo/trial`, `full_price`. | Ключевое поле для исключения ручных подписок и отделения платных продлений. |
| user_id | integer | Идентификатор пользователя. | Связь подписок пользователя и join с поведенческими таблицами. Не выводить списками в отчетах. |
| bank_alias | text | Нормализованный банк или канал оплаты: `superapp`, `freedom`, `kaspi`, `partner_billing`, `no_transaction` и др. | Анализ платежных каналов и выявление подписок без транзакции. |
| end_date | date | Дата окончания подписки. | Окно наблюдения продления и фильтрация поведения внутри подписки. |
| real_provider_id | integer | Исходный `provider_id` из `msp_ref_subscriptions`. | Аудит расхождений с нормализованным `provider_id`. |
| packet_id | integer | Идентификатор пакета/тарифа. | Правила нормализации source/provider и исключения тестовых пакетов. |
| start_date | date | Дата начала подписки. | Когортный отбор и сортировка подписок пользователя. |
| t_v_crdate | timestamp without time zone | Техническая дата создания/обновления записи витрины. | Контроль свежести витрины. |

## Ключевые поля

- `user_id` - ключ пользователя для связи подписок и поведенческих таблиц.
- `start_date` / `end_date` - период действия подписки.
- `sub_num` - номер подписки пользователя; для первой подписки использовать `sub_num = 1`.
- `payment_status` - разделяет ручные, trial/promo и полноценно оплаченные подписки.
- `provider_id` - нормализованный источник подписки.
- `real_provider` / `real_provider_id` - исходный источник, нужен для аудита.
- `packet_id` - основа правил фильтрации и нормализации.

## Ограничения

- Поле `phone` присутствует в витрине и используется для сопоставления с платежами, но его нельзя выводить в аналитические выборки, notebook или отчеты.
- `manual` не означает отсутствие подписки; это означает отсутствие найденного платежа при нетриальном/непромо типе. Для исследования продления такие строки нужно исключать из target или анализировать отдельным сегментом.
- Join подписки с платежом идет по `phone`, `start_date = cr_date` и порядковому номеру `rn`; возможны несовпадения, если платеж прошел не в дату начала подписки или есть несколько операций.
- Для партнерских пакетов `packet_id in (7, 60, 64)` цена задается правилом, а не берется из транзакции.
- `provider_id` в витрине нормализован по `packet_id` и может отличаться от `real_provider_id`.
- Витрина исключает пользователей только с `user_role = 'test'`; если есть другие признаки тестов, они должны быть добавлены в SQL формирования витрины.

## Использование в анализе продления первой подписки

Для следующей версии исследования поведения и продления:

- использовать `spark_dm.subscriptions_with_revenue` вместо `spark_bsns_vlt.msp_ref_subscriptions`;
- определять первую подписку через `sub_num = 1` или через сортировку по `start_date` после фильтрации витрины;
- ограничить провайдеров до нужных источников:
  - Freedom Media: нормализованный `provider_id = 1` или проверенный набор по `real_provider`;
  - Super App: нормализованный `provider_id = 8` или `real_provider = 'SuperApp'`;
- исключать или отдельно сегментировать `payment_status = 'manual'`;
- для целевой переменной `renewed_7d` считать следующую подписку только среди валидных подписок, где ручные продления не смешиваются с полноценным продлением;
- не выводить `phone`, использовать только `user_id` внутри SQL join и агрегировать результат до уровня пользователя.

Рекомендуемое правило для базового анализа:

```sql
where provider_id in (1, 8)
  and payment_status <> 'manual'
```

Если нужно изучать проблему SuperApp отдельно, строить отдельный разрез:

```sql
provider_id = 8
and payment_status in ('manual', 'full_price', 'promo/trial')
```

Так можно увидеть, насколько ручные подписки и проблема рекуррентных платежей искажали прежний анализ.
