# Analytics Documentation

Репозиторий для хранения и развития документации аналитики продукта Freedom Media.

## Зачем нужен этот репозиторий

Цель проекта — вести документацию аналитики в структурированном виде через GitHub, чтобы:

* хранить историю изменений;
* видеть, кто и когда менял документацию;
* описывать события, параметры, триггеры и метрики в едином формате;
* хранить экспорт GTM-контейнера;
* использовать CSV-таблицы как справочники для Power BI;
* в будущем подключить ИИ-агента, который сможет читать документацию, предлагать изменения и аккуратно работать с файлами через Git.

## Основная идея

Документация должна быть удобна одновременно для человека, Power BI и будущего ИИ-агента.

Поэтому используются разные форматы:

* Markdown — для текстовой документации;
* CSV — для справочников событий, параметров, платформ и владельцев;
* JSON — для технических экспортов, например GTM-контейнера.

## Разделы документации

### 1. Обзор аналитики

Файл: `docs/01_overview.md`

Общее описание аналитической системы продукта: какие источники данных используются, какие задачи решает аналитика и какие принципы используются при ведении документации.

### 2. Событийная модель

Файл: `docs/02_event_model.md`

Описание событийной модели продукта: какие события собираются, зачем они нужны, где используются и как связаны с пользовательскими сценариями.

### 3. Метрики

Файл: `docs/03_metrics.md`

Описание ключевых метрик: активные подписчики, регистрации, конверсии, отток, возвраты, просмотры, подписки и другие продуктовые показатели.

### 4. Дашборды

Файл: `docs/04_dashboards.md`

Описание Power BI-дашбордов: назначение, владельцы, используемые таблицы, фильтры, меры и бизнес-логика.

### 5. GTM

Файл: `docs/05_gtm.md`

Описание GTM-контейнера: теги, триггеры, переменные, правила публикации и особенности работы с веб-аналитикой.

### 6. Источники данных

Файл: `docs/06_data_sources.md`

Описание DWH-таблиц, API, внешних систем и связей между источниками данных.
Основная событийная документация хранится в папке `events/`.


### `events/events.csv`


Основной справочник событий.


Пример назначения файла:

* единый идентификатор события;

* основное название события;
* группа события;
* описание;
* владелец;

* статус события.

### `events/event_params.csv`

Справочник параметров событий.


Пример назначения файла:

* к какому событию относится параметр;
* название параметра;
* обязательность;
* описание параметра.

### `events/event_aliases.csv`

Справочник алиасов событий.

Этот файл нужен, потому что одно и то же логическое событие может называться по-разному на разных платформах.

Например:

* на web событие может называться `content_open`;
* в SuperApp событие может называться иначе;
* при этом оба названия должны ссылаться на один стабильный `event_id`.

Главный принцип: разные платформенные названия должны связываться с единым идентификатором события.

### `events/triggers.csv`

Справочник триггеров.

Файл описывает, при каких условиях должно отправляться событие: клик, показ, открытие экрана, успешная покупка, запуск плеера и другие действия пользователя.

## GTM

Экспорты GTM-контейнера хранятся в папке:

```text
gtm/exports/
```

Рекомендуемый формат имени файла:

```text
gtm_container_YYYY-MM-DD.json
```

Например:

```text
gtm_container_2026-06-05.json
```

Изменения по GTM описываются в файле:

```text
gtm/changelog.md
```

Перед добавлением GTM-контейнера в Git нужно проверять, что в JSON нет секретов, токенов, приватных ключей и других чувствительных данных.

## Принципы ведения документации

1. Одно логическое изменение — один коммит.
2. Названия коммитов должны быть понятными.
3. События должны иметь стабильный `event_id`.
4. Платформенные различия должны описываться через справочник алиасов.
5. Табличные справочники должны храниться в CSV.
6. Текстовая документация должна храниться в Markdown.
7. GTM-контейнер должен храниться как экспортированный JSON.
8. Изменения должны проходить через Git, чтобы сохранялась история.
9. Документация должна быть понятна не только текущему аналитику, но и будущим коллегам.
10. Структура должна быть удобна для будущей работы ИИ-агента.
